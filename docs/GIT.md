# Git workflow

Install [Git for Windows](https://gitforwindows.org/), or use MinGit, in the Windows environment running AD17. Under Wine, use Windows `git.exe`; the macOS Git executable cannot be launched as a Windows process. The panel finds standard Git installations and `%LOCALAPPDATA%\Altium17365\MinGit\cmd\git.exe`, or you can select an executable under **Git setup**. Git 2.31 or later is required for process-local authentication configuration.

**Follow active project** is enabled by default. The panel reads AD17's focused project and finds its Git working copy, including nested project folders and Git worktrees. Switching projects updates the checkout and repository together; an unlinked or unrelated Git project clears the previous sync target. In-flight operations keep their original project. **Open project** uses the current AD17 session.

For a new clone or a manual override, use **Manual setup**:

1. In **Projects**, use **Create project…** to name a new PCB project and choose its workspace folder, or select an existing project. Choose **Use selected project**. Alternatively, open **Git** and enter the repository URL and a Workspace access token directly. Direct Git does not need GraphQL project listing, but still requires a valid token and permission to access the project.
2. Choose a new or empty local folder and **Clone**, or choose an existing working copy and **Refresh status**. Existing working copies must have matching `origin` fetch and push URLs. Use the repository URL exactly as returned by Altium or copied from the project's existing Git remote.

   **Git setup** optionally accepts an existing checkout of the same project as a cache, preserving its edits and creating an independent copy with full history. Clone allows up to one hour and can be cancelled. New checkouts preserve repository line endings.
3. Choose **Open project** and select its `.PrjPcb` file. The connector opens it in the current AD17 session and resumes automatic following. New empty repositories are supported; cloning one from Projects creates a blank `.PrjPcb` and an AD26-style `.gitignore` locally without committing them. Existing ignore rules are preserved.
4. Edit the project. The panel monitors saved files, AD17's unsaved-document flags and local commits waiting to upload. Choose **Save to Server…** in the Git tab or the active document's **File** menu. It saves modified open documents inside this working copy, then shows the changed files and an optional comment field. Leaving it blank creates a commit with an empty message. Choose the files and select **Save to Server** to commit and push to `master`. Unchecked files remain local, including files already staged by another Git client. Configure `user.name` and `user.email` using your Git client if they are not already set.
5. **Push changes** sends existing local commits. **Pull changes…** first reviews any incoming server commits; Push changes and Save to Server offer that review when needed. If uploading fails, the local commit is retained and **Save to Server…** stays available. Update credentials or resolve the connection problem and retry; an upload retry does not create a second commit. **Commit selected** is also available separately.
6. **Pull changes…** lists updated files and any conflicts. Choose **Local** or **Server** for each conflicting file, including PCB/schematic binaries, deletions and file/folder collisions. Local means the version saved on this computer. Unrelated staged, unstaged and untracked files are preserved. Diverged histories create one local merge commit with an empty comment; upload it with Push changes.
7. Save unsaved editor tabs before pulling. Affected saved documents close and reopen. If the `.PrjPcb` itself changes, close its project before applying the pull. An existing Git merge/rebase must be finished or aborted first.

Open projects and the selected working copy are fetched in the background about every two minutes while connected. Only repositories listed in the connected workspace use its token; a manually entered token applies to the selected repository. **Fetch now** checks immediately. Incoming-commit counts and possible conflict warnings appear in the panel; fetching updates downloaded history while documents stay open. Uploads require an explicit action. If a native document save is cancelled or fails, the upload does not start. Document saves are limited to the configured working-copy folder.

Workspace tokens authenticate Git using HTTP Basic authentication (`token` as the username and the access token as the password). The panel supplies a repository-scoped header through the Git process environment, with credential helpers and redirects disabled. It does not put credentials in command arguments, repository URLs, Git config or saved preferences. A project selected through an OAuth connection uses its refreshed Workspace token; replace an expired manually supplied token yourself. **Log out** in the panel header clears the session and direct Git token.

Repository URLs, folder paths and your Git executable preference are saved locally. This synchronizes project source files; it does not implement cloud releases, managed components or conversion of newer document formats. See Altium's [Project Git Access](https://www.altium.com/documentation/altium-developer-center/altium-365/key-concepts/project-git-access) documentation.


Pull reviews use temporary Git indexes. Applying a review rechecks local files, staging and the downloaded server revision, and retains the originals under `refs/altium17365/recovery/<id>/{worktree,index,head}`. These local recovery refs are not pushed. If an interrupted pull leaves `index.lock`, keep it and inspect those snapshots with a Git client before continuing. Existing locks owned by another Git operation are preserved.
